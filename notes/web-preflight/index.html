3.02k visitors overnight. None of them were people.

How a parked landing page on caffeinity.com turned into the web-preflight skill.

Abdul Rahman P Z · Notes

The launch

I already owned caffeinity.com, and for a while all it had was a coming-soon page. I also had a landing page I'd built and then parked. So I thought, why not get it back up and deploy it? I put it on Cloudflare. It was a static site: no server code, no database, no login.

The numbers

The next day I opened Cloudflare Web Analytics. 3.02k visitors. Most of them from Japan and South Korea, some from the United States, and a scattering from elsewhere.

I was thrilled. In my head there was already a market for Caffeinity in Japan. I was planning an anime-themed post, and a Q&A on Japan and coffee.

The status codes

Being a pessimist, I kept looking. Some requests were 200s. Many were 404s and 403s. A one-page landing site doesn't get a pile of 404s from real visitors, so I opened up the paths. They were asking for /.env, /.git/config, /wp-login.php, /phpinfo.php, .ini config files. None of those had ever existed on my site.

I took a screenshot and pasted it into Claude, ChatGPT, Duck.ai and Gemini. What came back was a shock. They were crawlers, bots that go through every new site looking for whatever a deploy left behind: environment files with API keys in them, Git metadata, PHP config, admin and debug pages. They don't care what the site is. A new domain coming online is enough.

Why it didn't hurt, this time

The 200s were my real pages. Everything the bots asked for came back 404 or 403. Claude, ChatGPT and Duck.ai all said the same thing: for a static landing page, this wasn't serious. If it had been a server-rendered app with a .env sitting in the deploy folder, it would have been a catastrophe.

So I was safe because there was nothing to find, not because I had checked.

How most people ship

Think about how most people deploy a website now, especially vibe coders and anyone who doesn't come from IT. It runs fine locally, so it goes to production. Nobody checks what else went up with it. The bots do, and they get there within a day.

So it became a skill

That's web-preflight. Before you call a release done, your agent asks your site for the same things the bots ask for: a fixed list of 19 paths, including the .env variants, .git/HEAD and .git/config, package and composer files, wp-admin, phpinfo and server-status. Then it tells you what actually came back.

It's bounded on purpose. Requests and bytes have hard limits, nothing sensitive is written to disk, and it's only for a site you own. It isn't a scanner or a penetration test.

It also reads the answer, not just the status code, which is the lesson from my own logs. A 200 on /.env from a single-page app is usually the homepage served for every path, not your secrets. A firewall blocking everything doesn't prove the site behind it is clean. When it can't tell, it says INCONCLUSIVE. It never calls that a pass.

The fans in Japan

They were my own projection. The anime post and the Japan coffee Q&A went up in steam. What I got instead was a check I now run before every deploy. I'd like you to run it before the bots get to your site.
