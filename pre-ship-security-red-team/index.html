how it works

Three groups, three account sets, one fixer.

The subagents attack and record — scenario id, preconditions, safe reproduction, redacted request and response, expected versus actual, evidence location. They never fix, never edit application files, never touch accounts. The chair consolidates duplicates, fixes centrally in blast-radius order, then reruns.

Identity & authorization 1 · high effort

The failures that expose or destroy someone else's data.

  • S01 anonymous database or API access
  • S02 cross-user object access (IDOR/BOLA)
  • S03 self-service privilege escalation
  • S04 password-reset token reuse

UI bypass & input 2

Where the client was trusted and the server agreed.

  • S05 direct request bypass of UI limits
  • S06 free-tier or quota bypass
  • S07 concurrent quota race
  • S08 input validation and boundaries
  • S09 redirect validation

Browser, network, cache, AI 3

Everything that leaves the request/response pair.

  • S10 stored XSS
  • S11 SSRF, local mock server only
  • S12 private response and cache isolation
  • S13 preview deployment access
  • S14 prompt injection through ingested content

One isolated account set each no collisions

User A, User B and Admin per group, prefixed g1a@test.invalid so two subagents never write the same rows and cleanup stays mechanical. The chair creates and deletes them; subagents never promote or remove an account.

  • one browser context per group
  • synthetic rows only, never a prod copy
  • each group fills only its own file
  • sequential fallback if subagents are unavailable

The evidence contract all

Scaffolded into .pre-ship-red-team/<run-id>/: gate.md, an ignored .env written before the first test credential exists, one brief and one results table per group, capture directories, then report.md. Verdicts are pass, fail, not-proven, not-applicable — unrun is the scaffolded default and always fails the check. After the fixes, check_results.mjs --require-fixes exits 1 on a missing row, a pass without a captured request and response, a fix without its negative control, or an unmasked credential anywhere in the run directory.

  • 14 rows, no adding or removing
  • negative control: remove the guard, watch it fail, restore it
  • a durable regression test per finding
  • ship posture HOLD or ready, scoped to what ran

how the fixes were proved

Twice, not asserted: the committed rerun suite returns 14 REFUSED / 0 DETECTED, and a mutation harness deletes one protection at a time on a throwaway copy of the server and requires the mapped check to flip back to DETECTED — 17 of 17 protections falsified. That second run is what makes the first one meaningful; a suite that only ever passes cannot tell you whether it can see dirt.

every row carries its method, request, response and severity in results/group-<n>.md, and the checker refuses the run until each row is filled, evidenced and masked--require-fixes additionally blocks any surviving fail

Read the table with its limits, which the run records in report.md: it shows what the rig planted, not what an average app contains; six controls in the rig held at baseline, so 13-of-14 is a fixture property; the S12 proof is header-level because no shared cache sits in front of a loopback server; the browser dialog proof exists for the before state only; and the hosting-platform preview class (Vercel, Netlify, Cloudflare) was never reachable from a local run.

Also verified, independently of the app: the scaffold and the checker are tested against 11 fixture outcomes — unfilled rows, code-only passes, legitimate not-applicable rows, open fails allowed pre-fix and blocked with --require-fixes, fixes without a negative control, an unmasked JWT planted in a capture — all passing. This is a pass rate over 14 checks, not a claim that an app is free of vulnerabilities, and it never calls anything secure.

what it will not do

Nine gates, and a hard no.

Anything you do not own

Explicit ownership or explicit authorization, and nothing outside the approved environment. No third-party systems, no real users, no real payment flows — payments in test mode only, and the mode is confirmed from the key itself, not from the filename.

Production, ever

Local or isolated environments only, never production. A preview that shares the production database is production: a non-local --app-url is flagged in the written gate, and the checker refuses to certify a report whose gate was never filled in.

Hammer an endpoint

The concurrent-quota test defaults to five requests; twenty only on your explicit approval for a local-only test. It backs off on 429 or 503, stays inside the per-group request budget recorded in the gate, and stops the run on instability or any sign of production connectivity.

Real metadata or live attacker sites

SSRF uses a local mock server and reserved .invalid destinations; redirects go to .test hosts. It never loads a third-party origin, never port-scans past the app's own origin, and never calls a real cloud metadata endpoint.

Commit credentials or raw responses

Passwords stay in a git-ignored .env written before the first credential exists; tokens and personal data are masked in every artifact. And it changes nothing you did not approve: no plugin installs, no dashboard or configuration edits, no external deletions, no commits or pushes.

Call your app "secure"

It reports what ran, what was refused and what was never proven, with a ship posture of HOLD or ready scoped to what was tested, and a named list of every row that never ran. Fourteen passing rows is evidence about fourteen checks — not proof of no vulnerabilities.
